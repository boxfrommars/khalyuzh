# Deployment requirements: `Рацион Халюжа`

Этот документ описывает требования приложения и проверяемый результат
размещения. Он не задаёт конкретный хост, абсолютные пути, пользователей ОС,
права файлов, процесс передачи релиза или инструменты окружения размещения.

Значения секретов, production-конфигурация, приватные ключи, сертификаты, базы
данных и резервные копии в репозиторий не добавляются.

## Приложение

| Параметр | Значение |
| --- | --- |
| Название | `Рацион Халюжа` |
| Репозиторий | `git@github.com:boxfrommars/khalyuzh.git` |
| Production-ветка | `main` |
| Канонический URL | `https://khalyuzh.dgroza.ru/` |
| Тип процесса | HTTP request |
| Runtime | PHP 8.3 |
| База данных | SQLite |

## Runtime-интерфейс

- Package manager: отсутствует.
- Установка production-зависимостей: не требуется.
- Относительный публичный каталог: `public`.
- HTTP entry points:
  `public/index.php`, `public/api.php`, `public/admin/index.php` и
  `public/admin/api.php`.
- Frontend-сборка: отсутствует.
- Требуемые системные возможности:
  PHP 8.3 с расширениями `PDO` и `pdo_sqlite`; для штатного резервного
  копирования также нужен `sqlite3` CLI.
- Интеграция с HTTP-сервером:
  запросы передаются в соответствующие PHP entry points; административные
  маршруты защищаются HTTP Basic Authentication на уровне веб-сервера.
- Ограничения процесса:
  приложение обрабатывает отдельные HTTP-запросы и не запускает long-running
  или singleton-процесс.

Все пути в этом документе заданы относительно корня приложения. Способ запуска
PHP и его интеграцию с HTTP-сервером выбирает окружение размещения.

## Конфигурация

Переменные окружения приложению не требуются.

Для административных entry points веб-сервер обязан передавать
аутентифицированное имя пользователя в `REMOTE_USER` или `PHP_AUTH_USER`.
Запрос к административному PHP entry point без такого подтверждения
отклоняется с HTTP `403`. Учётные данные HTTP Basic Authentication являются
секретом окружения размещения и не хранятся в репозитории.

Параметры профиля, названия кормов, калорийность и диапазон нормы задаются в
`app/config.php` и поставляются вместе с кодом.

## Состояние и запись

- Writable-пути runtime относительно корня: `storage`.
- Генерируемые артефакты:
  `storage/backups/records-*.sqlite`, создаваемые командой `bin/backup.sh`;
  скрипт сохраняет последние 30 копий.
- Постоянные данные: `storage/records.sqlite`.
- Пользовательские загрузки: отсутствуют.
- Требование к согласованной backup-копии:
  копия базы создаётся через SQLite `.backup` командой `bin/backup.sh`;
  обычное файловое копирование открытой базы не считается согласованной
  резервной копией.
- Проверка целостности и восстановления:
  `sqlite3 storage/records.sqlite 'PRAGMA integrity_check;'` должна вернуть
  `ok`; восстановление необходимо периодически проверять на отдельной копии
  базы без изменения production-данных.

`storage/records.sqlite` и резервные копии являются постоянными данными и не
должны удаляться или заменяться вместе с checkout кода.

## Lifecycle hooks

Обязательные lifecycle hooks отсутствуют.

Создание файла базы и таблицы `records` выполняется приложением идемпотентно при
первом обращении к базе и не является отдельным deployment hook.

## Изменения данных

- Миграции: отсутствуют.
- Предусловия: отсутствуют.
- Обратимость: не применимо; текущий релиз не меняет существующую схему.
- Ожидаемая недоступность: отсутствует.
- Совместимость старой и новой версии с данными:
  текущая версия использует одну таблицу `records` и выполняет только
  `CREATE TABLE IF NOT EXISTS`; существующие строки не преобразуются.

Если будущий релиз изменит схему или смысл постоянных данных, до его выпуска
необходимо добавить явную миграцию, предусловия backup и правила rollback в
этот документ.

## Внешнее поведение

- Канонический URL: `https://khalyuzh.dgroza.ru/`.
- Дополнительные имена: отсутствуют.
- Redirects:
  любой HTTP URL на `khalyuzh.dgroza.ru` возвращает `301` на тот же путь и query
  string по HTTPS; `/admin` возвращает `301` на `/admin/`.
- Health endpoint:
  отдельный endpoint отсутствует; для read-only smoke-проверки используется
  `GET /api.php`, который возвращает HTTP `200`, JSON и массив `records`.
- Поведение неизвестного URL:
  HTTP `404`; произвольные PHP-файлы, dotfiles и неизвестные пути не
  публикуются.

Ключевые read-only smoke-сценарии:

| Метод и путь | Ожидаемый результат |
| --- | --- |
| `GET /` | `200`, HTML-страница с заголовком «Рацион Халюжа» |
| `GET /api.php` | `200`, `application/json`, верхнеуровневое поле `records` содержит массив |
| `GET /admin` | `301` с переходом на `/admin/` |
| `GET /admin/` без учётных данных | `401` и запрос HTTP Basic Authentication со стороны веб-сервера |
| `GET /admin/` с корректными учётными данными | `200`, административная HTML-страница |
| `GET /admin/api.php` с корректными учётными данными | `200`, `application/json`, верхнеуровневое поле `records` содержит массив |
| `GET /несуществующий-путь` | `404` |
| `GET /.git/config` | `404` |

`PUT /admin/api.php?date=YYYY-MM-DD` и
`DELETE /admin/api.php?date=YYYY-MM-DD` изменяют постоянные данные и не входят
в read-only smoke-проверку.

## Проверка релиза

Команды, которые подтверждают готовность кода независимо от способа
размещения:

```shell
find app public -type f -name '*.php' -exec php -l {} \;
php -r 'exit(extension_loaded("PDO") && extension_loaded("pdo_sqlite") ? 0 : 1);'
sh -n bin/backup.sh
```

После размещения вручную выполнить read-only smoke-сценарии из раздела
«Внешнее поведение», проверить HTTPS и канонический redirect, затем запустить
backup и проверить созданную копию на отдельном тестовом экземпляре.

## Совместимость rollback

- Можно ли вернуть предыдущую версию кода без возврата данных:
  да, если предыдущая версия совместима с текущей таблицей `records`.
- Application-команды после возврата кода: отсутствуют.
- Требуется восстановление данных:
  нет для обычного возврата текущих совместимых версий; требуется только при
  повреждении данных или после будущего несовместимого изменения схемы.
- Несовместимые изменения:
  в текущем релизе отсутствуют; любое будущее изменение схемы должно отдельно
  определить совместимость rollback.
- Проверки после возврата:
  `GET /`, `GET /api.php`, аутентификация `/admin/`, ожидаемые `404` и
  `PRAGMA integrity_check`.

Выбор версии, переключение checkout и другие действия окружения размещения в
этот документ не входят.

## Когда обновлять этот документ

Обновить `DEPLOYMENT.md`, если меняются runtime, production-зависимости,
переменные окружения, публичный интерфейс, writable-потребности, постоянные
данные, lifecycle hooks, миграции, внешнее поведение или совместимость
rollback.

Обычное изменение контента или исправление кода не требует обновления
документа, если требования приложения остаются прежними.
